## Consumer-supporting widenings (3 files, in scope)

These 3 files were not directly errored but their interface
declarations were widened so the colocated callers (above) type-check
without touching the call sites further. All within `src/components/`,
all pure type-level:

- `AccountMenu.tsx` -- widened `theme?: ThemeMode \| undefined` and
  `onThemeChange?: ((next: ThemeMode) => void) \| undefined` to satisfy
  `Sidebar.tsx(263,12)`.
- `ui/alert.tsx` -- widened `AlertProps`'s own optional fields
  (`variant / title / children / icon / action / dismissible / onDismiss
  / role / size / className`) to `T \| undefined` to satisfy
  `ui/alert-banner.tsx(76,6)` (the wrapper destructures + re-spreads
  these props, picking up `T \| undefined` after the destructure,
  which then violated AlertProps's narrower `T?` slots).
- `ui/dropdown-menu.tsx` -- widened `DropdownMenuProps.placement /
  ariaLabel / header / className` to `T \| undefined` to satisfy
  `LocaleSwitcher.tsx(93,6)`.

## Risk

- Pure type-level edits. The interface widenings to `T \| undefined`
  are structurally identical to `T?` at runtime (every consumer
  already passes either a defined value or `undefined`), so no
  behaviour can shift.
- The two `Omit<..., 'title'>` extends-clauses (PanelProps,
  WidgetHeaderProps) drop `HTMLAttributes.title` from the inherited
  shape, which means a caller can no longer pass the HTML `title=`
  tooltip-string attribute to those primitives. Source grep confirms
  no Panel / Widget call site does -- both use the ReactNode `title`
  prop as the rendered slot, not the tooltip attribute.
- The detail-panel `__type?` cast widens the read shape; the existing
  `===` symbol equality checks already correctly treat `undefined` as
  a non-match, so the if/else branches behave identically.
- The WorkerResourceGraph `if (!latest) return null` is on a code
  path the existing `samples.length === 0` early-return already
  blocks, so the null render is unreachable at runtime; the guard
  exists purely to narrow for tsc.
