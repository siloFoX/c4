# 11.1144 - fix 3 fake-timer/clipboard test-infra failures across 2 files

## Scope

2 test files, 3 failing assertions. All 3 are TEST-INFRA bugs (incorrect
fake-timer + userEvent integration), NOT real source bugs. Fixed
test-only without raising any timeout and without deleting any timing
assertion. ZERO source files touched. Both files now pass deterministically
under two consecutive vitest runs.

## Per-file root cause and fix

### 1. `src/lib/use-stuck-meetings.test.ts` (1 case)

**Failing case:** `refetches on the 60s poll interval and updates with
the latest payload` -- timed out at 5000ms.

**Root cause:** The test installed `vi.useFakeTimers()` and then asserted
each interval result through `await waitFor(() => expect(result.current
?.count).toBe(N))`. `waitFor` from `@testing-library/react` drives its
predicate via an internal `setInterval` (default 50ms) + a
`setTimeout` budget (default 1000ms). Under `vi.useFakeTimers()`,
BOTH those internals are faked, so `waitFor`'s predicate never re-runs
and its timeout never trips. The test hung until vitest's 5000ms
testTimeout (real-time) bailed.

The first probe `await vi.advanceTimersByTimeAsync(0)` flushes ONE
microtask round, but `apiGet` is a multi-await chain (`await apiFetch`
then `await res.json()` then `.then(setData)`) AND MSW v2 schedules its
intercept resolve through an internal setTimeout(0)-like hop. A single
0-advance does not flush all of these on the first poll.

**Fix:** Replace `vi.useFakeTimers()` with `vi.useFakeTimers({
shouldAdvanceTime: true })`. With `shouldAdvanceTime`, real wall-clock
progress is mirrored onto the fake clock (default 20ms delta) so
`waitFor`'s internal interval still fires, MSW's internal setTimeout(0)
fires, and the apiGet promise chain settles -- while the deterministic
`vi.advanceTimersByTimeAsync(60_000)` calls still jump the
`setInterval(tick, 60000)` boundaries explicitly so the test never
actually sleeps 60 real seconds. Each interval boundary plus
`waitFor(...)` confirms the expected count.

Determinism: two consecutive runs of the file (vitest run) both report
**1 file pass + all cases pass**; this case completes in well under the
5000ms budget (no real 60s wait).

### 2. `src/components/ui/data-list.test.tsx` (2 cases)

#### 2a. `invokes navigator.clipboard.writeText with the copyValue on click`

**Failing:** `[AsyncFunction writeText] is not a spy or a call to a spy!`

**Root cause:** The file's `beforeEach` installs
`navigator.clipboard = { writeText: vi.fn().mockResolvedValue(...) }`,
but `userEvent.setup()` (v14+) installs its OWN clipboard simulation
that overwrites `navigator.clipboard`. By the time
`handleCopy -> copyTextToClipboard -> navigator.clipboard.writeText`
fires, the value at `navigator.clipboard.writeText` is userEvent's
implementation, not the vi.fn() the assertion checks. The assertion
fails because the live reference is not a spy.

**Fix:** Spy on the live `navigator.clipboard.writeText` surface AFTER
`userEvent.setup()` has wired its own clipboard, then assert on that
spy. `vi.spyOn(navigator.clipboard, 'writeText')` wraps the live method
so calls are recorded; the test's intent ("clicking the copy button
calls writeText with the copyValue") is preserved exactly.

#### 2b. `shows a Check icon transiently after copy and reverts after the timer`

**Failing:** test timed out at 5000ms.

**Root cause:** Same as case 1's class of bug, but inside
`await user.click(btn)`. The test did `vi.useFakeTimers()` first, then
`userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`. userEvent
v14 awaits a chain of pointer-event microtasks plus the async clipboard
write inside `handleCopy`; the sync `vi.advanceTimersByTime` callback
never gives the microtask queue a chance to drain, and userEvent's
internal Promises hang forever.

**Fix:** Replace `vi.useFakeTimers()` with `vi.useFakeTimers({
shouldAdvanceTime: true })` and drop the `advanceTimers` option to
`userEvent.setup()`. With `shouldAdvanceTime`, userEvent's internal
awaits resolve as wall-clock progresses; `vi.advanceTimersByTime(1300)`
still deterministically fires the 1200ms `setTimeout(... => setCopied
(false), 1200)` inside `handleCopy`, preserving the original timing
assertion verbatim.
