# 11.1146 - rewrite NewChatModal initial-focus test to be JSDOM-safe (Option 1: structural check)

## Scope

`src/components/NewChatModal.test.tsx`'s `focuses the prompt textarea
on mount` case failed ONLY in JSDOM. Production behavior is correct
(verified in 11.1142). Rewritten to verify the structural conditions
that drive a real browser's focus pick, without depending on JSDOM's
buggy multi-selector `querySelectorAll` ordering.

**Option used:** Option 1 (BEST) - keep the test in JSDOM, rewrite the
assertion to verify intent (textarea is the first focusable element
inside the dialog by document order) instead of the JSDOM-fragile
`toHaveFocus()` check. No browser test file needed; no `it.skip`.

## Root cause (recap from 11.1142)

- `NewChatModal.tsx:68` sets `autoFocus` on the prompt `<textarea>`.
- The component is wrapped in `<Dialog>` (`src/components/ui/dialog.tsx`)
  whose `useFocusTrap` effect calls `focusables[0]?.focus()` on mount
  using `container.querySelectorAll(FOCUSABLE_SELECTOR)` where
  `FOCUSABLE_SELECTOR` is the 10-clause list in
  `src/hooks/use-focus-trap.ts:11-22`.
- A binary-search diagnostic in 11.1142 isolated the cause to the
  `summary:not(:disabled)` clause: when JSDOM's `querySelectorAll`
  is given that 10-clause list, it returns
  `<select id="new-chat-model">` BEFORE
  `<textarea id="new-chat-prompt">`, even though the textarea
  precedes the select in document order. Real browsers (per the
  CSS spec) always return document order regardless of selector
  list shape, so `focusables[0] === textarea` and initial focus
  lands on the textarea correctly.

## Rewrite (Option 1)

The new assertion walks the dialog tree depth-first and applies the
same per-element focusability predicate as
`src/hooks/use-focus-trap.ts:24-28` (`getFocusables`), independent of
`querySelectorAll`. It asserts that the first focusable element found
in document order is the prompt textarea. This is exactly the
structural condition that produces "initial focus = textarea" in any
spec-compliant browser. The rewrite:

- Uses a manual recursive walk (not `querySelectorAll`), so JSDOM's
  multi-selector ordering bug is bypassed.
- Mirrors the focus-trap's own focusability rules (disabled check,
  tabindex >= 0, focusable tags, contenteditable, etc.), so the
  test stays load-bearing for the actual contract.
- Does NOT assert `toHaveFocus()` directly (JSDOM cannot be trusted
  here for this dialog's particular focus-trap selector). The test
  instead pins the load-bearing precondition.

The assertion fails the moment a regression inserts ANY focusable
element ahead of the textarea inside the dialog (which is what would
actually break the UX). It is therefore not a weaker test - it is a
tighter test of the right invariant.

A multi-line comment block at the top of the case names the bug, the
diagnostic from 11.1146, and the JSDOM-vs-spec deviation, so a future
reader does not have to re-derive the rationale.
