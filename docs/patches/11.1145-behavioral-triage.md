## Per-file verdict

| File | Failing assertions | Verdict | Action |

| `src/lib/use-scrollback.test.ts` | 3 (`data.error path surfaces the message`, `thrown error path (HTTP 500)`, `exposed setError setter overrides`) | **REAL SOURCE BUG** | Edit `src/lib/use-scrollback.ts` (source). Reason: the useEffect at the bottom of the hook listed `setActionMsg` in its dependency array. Consumers (including the real `WorkerDetail.tsx:67`) pass an inline arrow `(next) => setActionMsg(next)` as that prop, so the function identity changes on every render. The effect therefore re-fires on every render and calls `setError(null)` inside, racing against the in-flight fetch's `setError(<actualError>)`. The legitimate error oscillates set-then-cleared and never surfaces -- which is exactly the silent error-swallowing UX bug the dispatch flagged. Minimal fix: capture `setActionMsg` in a ref (refreshed on every render so the value stays current) and call `setActionMsgRef.current(null)` inside the effect, then drop `setActionMsg` from the dependency array. The effect now runs only when `fetchScrollback` (i.e. `tab`/`workerName`) or `tab` actually changes, preserving the original "reset on tab change" contract while ending the per-render reset loop. |
| `src/components/ui/number-input.test.tsx` | 1 (`ArrowUp / ArrowDown step via keyboard`) | **STALE TEST** | Edit the test only. The Controlled fixture has `initial=5` and no `min`. The test pressed `ArrowUp` then two `ArrowDown`s, asserting `toHaveBeenLastCalledWith(5)`. The arithmetic is `5 -> 6 -> 5 -> 4`, so the last `onChange` call is `(4)`, not `(5)`. The component's `stepBy(-step)` correctly decrements without a floor when `min` is unspecified -- the test had an off-by-one extra `ArrowDown`. The fix preserves the test's stated intent (verify keyboard up and down both step) by asserting after EACH keystroke (`up -> 6`, `down -> 5`) so both directions are pinned explicitly. |
