### 1. NewChatModal.test.tsx (1 failing test) - REPORT (real env bug, NOT edited)

**Test:** `focuses the prompt textarea on mount` expects the prompt
`<textarea>` (id `new-chat-prompt`, has `autoFocus`) to receive focus
on mount. Actual: the `<select id="new-chat-model">` receives focus.

**Triage:**

- Source `web/src/components/NewChatModal.tsx:68` still carries
  `autoFocus` on the prompt textarea. The intent is clear.
- The component is wrapped in `<Dialog>` which uses
  `useFocusTrap(cardRef, { active: open, ... })`
  (`web/src/components/ui/dialog.tsx:118`).
- `useFocusTrap` runs in a `useEffect` after React's commit-phase
  `autoFocus` and unconditionally focuses
  `getFocusables(container)[0]` (`web/src/hooks/use-focus-trap.ts:51-52`).
- `getFocusables` builds the list with
  `container.querySelectorAll(FOCUSABLE_SELECTOR)`. `FOCUSABLE_SELECTOR`
  (`use-focus-trap.ts:11-22`) is a 10-item comma list including
  `summary:not(:disabled)`.
- A binary-search diagnostic (built in a throwaway debug file then
  deleted) showed: in JSDOM, **adding `summary:not(:disabled)` to
  the selector list flips `querySelectorAll`'s return order** from
  document-order to a permutation that puts `SELECT#new-chat-model`
  ahead of `TEXTAREA#new-chat-prompt`. With any subset that excludes
  `summary:not(:disabled)`, JSDOM returns document order
  (textarea-first) as expected.
- In real browsers, multi-selector `querySelectorAll` strictly
  returns document order regardless of selector list shape, so
  `focusables[0]` is the textarea and production focus is correct.

**Verdict:** REAL bug, but the bug surface is a JSDOM-vs-spec
deviation interacting with `summary:not(:disabled)` in the shared
focus-trap selector. The test's expectation (textarea receives
focus) matches the source's stated intent and the production
behavior. Touching this test to assert the JSDOM-observed (wrong)
behavior would lock in a JSDOM quirk and mis-test the component.
Per contract, **left failing - reported here for human review**.
Source-side options (for a future TODO): re-order
`FOCUSABLE_SELECTOR` so `summary:not(:disabled)` is last, or
post-sort `getFocusables` by document position via
`compareDocumentPosition` so JSDOM's quirk is neutralized at the
source.

### 2. WikiBulkPublishRow.test.tsx (1 failing test) - STALE (fixed)

**Test:** `wraps the row in a flex container with the border-t and
pt-2 classes` asserts `container.firstChild` has `flex`, `border-t`,
`pt-2`. Actual: `firstChild` has `w-full border-t border-border`.

**Triage:**

- `TODO 11.147 / v1.11.165` (commit f25102c9 "feat(ui): separator
  primitive") refactored the row from a single
  `<div className="flex flex-wrap items-center gap-2 border-t
  border-border/60 pt-2 ...">` to `<><Separator /><div
  className="flex flex-wrap items-center gap-2 pt-2 ...">...</div></>`.
- `container.firstChild` is now the `<Separator>` (a `<div
  role="...">` with the border-t equivalent) rather than the flex
  wrapper. The `border-t` class moved INTO the Separator primitive
  by design.
- The intent (visible divider above + flex row with `pt-2`) is
  preserved; only the markup structure changed.

**Fix:** Target the flex container directly via
`container.querySelector('div.flex')`, retain the `flex` + `pt-2`
assertions, drop the `border-t` assertion (now owned by Separator).
Updated test name + added a comment naming TODO 11.147 / v1.11.165.

### 3. safe-area.test.ts (1 failing test) - STALE (fixed)

**Test:** `web/package.json is bumped to 1.11.215` asserts
`pkg.version === '1.11.215'`. Actual: `1.11.1159`.

**Triage:**

- The version pin (1.11.215) marked the safe-area mobile-viewport
  release at the time the test was authored.
- Hundreds of subsequent bumps have moved the live version far past
  that floor. The actual safe-area behavior is exercised by the
  other 8 tests in this file (viewport meta, theme-color, tailwind
  safe-* tokens, css fallback, main.tsx import, AppHeader/Sidebar/
  Toast usage). The literal version pin tested nothing that hadn't
  already been re-verified by those assertions.

**Fix:** Replaced the exact-string pin with a segment-wise
floor check (`version >= 1.11.215` compared lexicographically over
`[major, minor, patch]`). Renamed the test
`web/package.json is at or past the safe-area landing version
1.11.215` and added a comment naming the original release
context. The floor remains load-bearing (a downgrade past it
fails); the test no longer needs an update on every bump.
